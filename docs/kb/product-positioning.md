## 0. 一句話定位

> **owx 是一個專門做「文件開發」的配套 AI agent chat。**
> 以**文件**（需求／規格／決策／知識）為一等公民，讓 agent 與人在**同一張會演化的知識圖**上**共同開發文件**，並以**標準為紀律**，產出**可證的 traceability 與治理**。

「配套」（companion）指的是：它不是取代人的自動化，而是與人**並肩開發文件**的 agent chat——人負責判斷與決策，agent 負責紀律、產出、追溯與守門。

---

## 1. 問題：AI 開發的瓶頸不是「寫程式」，是「把問題說清楚」

- coding agent（opencode／Cursor 等）已成熟——**寫程式**不再是主要瓶頸。
- 企業真正的瓶頸在**文件**：需求沒理清、規格漂移、決策沒留痕、治理無從稽核。
- 這些文件的產出、維護與追溯，仍是**人工、易腐、不可證**的。

> **程式語言會變，需求不會變。** 真正該被 agent 操作的**原生物件是「文件／知識」**，coding 只是其特例。

---

## 2. 這是什麼 / 不是什麼

| 面向 | owx **是** | owx **不是** |
|---|---|---|
| 對象 | **文件開發**（需求／規格／ADR／知識）的共同作者與守門人 | 以程式碼為中心的 coding copilot |
| 介面 | **配套 agent chat** ＋ 文件工作面（Explorer／Outline／Preview） | 文件瀏覽器、內容網站、文章清單 |
| 治理 | 以**標準為紀律**、**可證 traceability** | 無治理的通用聊天 |
| 邊界 | 疊在 opencode（MIT substrate）之上、包裝不擴充 | 重寫 AI 邏輯、與 opencode/omo 競爭 coding |

---

## 3. 目標使用者與場景

- **企業內部**：問題理清、案例研究、公司治理的基礎工具。
- **角色**：需求／規格作者、架構師、PM、法遵與品質負責人。
- **場景**：以「**文件專案**」為單位（`~/knowledge/<專案>`），從需求 → 規格 → 決策 → 知識，**逐輪迭代、回寫規格**。

## 5. 差異化

| 對照 | 他們 | owx |
|---|---|---|
| **coding agents**（opencode／Cursor） | 以程式碼為中心 | **以文件為中心**；coding 是特例 |
| **文件工具**（Notion／Confluence／編輯器） | 只是編輯與瀏覽 | **agent 共同開發 ＋ 治理** |
| **RAG 問答** | 檢索**既有**文件 | **開發與演化**文件 |
| **通用 chat** | 無紀律、無追溯 | **標準為紀律**、可稽核 |

**唯一楔子**：requirements・docs・code **共用一張知識圖**，agent 以標準強制它 → 賣**可證的 traceability 與治理**。

---

## 6. 楔子與北極星

- **楔子（Wedge）**：需求／規格文件的**共同開發 ＋ traceability**——先在一類文件上做到「可證」。
- **北極星（North Star）**：企業在「問題理清、案例研究、公司治理」的基礎工具。

---

## 7. 為什麼是現在

- LLM 讓「文件」從**死的文字**變成**可操作的對象**（可協作、可驗證、可追溯）。
- 文件即**知識資產**：可 diff、可審核、可進 git、可被 RAG 佐證。
- 治理與合規需求上升，但工具仍停在「人寫、人審、無追溯」。

---

## 8. 現況 vs 願景（誠實）

- **現況（第一階段）**：文件優先 IDE 骨架、專案生命週期、配套 chat 與完整指令面**已可用**；標準本體、共用知識圖／GraphRAG、模組微服務**尚未實作**。
- **願景**：以文件為原生物件、以標準為紀律，成為企業「問題理清 → 案例研究 → 公司治理」的基礎工具——**可證、可稽核、可演化**。

> 定位不是宣告完成，而是**收斂方向**：之後每一輪迭代都應回問——「這一步是否讓『文件開發的配套 agent chat』更真？」
