# ADR-0002：工作流由「瀑布」改為「迭代螺旋」

- **Status**：Accepted
- **Date**：2026-10-17
- **Deciders**：Daniel（專案負責人）

## Context

初版 `AGENTS.md` §0 採四階段瀑布：① 回溯規格 → ② 調整功能 → ③ 開發 → ④ 驗收，並設下**「規格（§9 待決）未拍板前不得動工」**的一次性閘門。實務推進時發現三個問題：

1. 回溯出的「基礎核心規格」本質是**通用 code agent 規格**，與「文件優先」目標之間存在 5 項缺口（見 `base-core-requirements.md` §7）——這些缺口**難以在純規格階段拍定**，須以實作驗證收斂。
2. D1（語言/邊界）影響 2x+ 工作量，但更適合先用**一條 vertical slice** 驗證架構可行性，再由實作回吐需求。
3. 專案**尚無程式碼**，純規格推演易與現實脫節；且已具備 substrate（opencode）可即早打通路徑。

## Decision

採**迭代螺旋**（見 `AGENTS.md` §0 Mermaid 圖）：

```
① 翻寫功能規格 → ② 立技術框架與前端界面 → ③ 實作功能並驗證測試
   → ④ 需求回流（修改/擴增 → 形成文件）→ ⑤ 持續實作（loop 回 ③）
```

- **廢除**「規格未拍板不得動工」的一次性閘門；改為**每輪迭代結束必須回寫規格**——規格落後於實作，視為該輪未完成。
- 規格與現實衝突時：**以實作驗證為準**，回頭更新規格，不無依據選邊。
- **第一階段**即：翻寫功能規格（另立 `functional-spec.md`）→ 建 Rust+React 框架與前端界面 → 實作功能並驗證測試 → 需求回流形成文件 → 持續實作。

## Consequences

**正面**
- 以**可行性驗證**驅動規格演化，避免規格空轉。
- 早期建立 walking skeleton，技術風險（跨語言邊界、substrate 整合）提前暴露。

**負面 / 成本**
- 規範的「規格」與「實作」須持續同步；以「未回寫即該輪未完成」作為約束。
- 需更頻繁的規格維護成本。

**可追溯**
- 每個缺口/決策仍以穩定 ID（`FR-*` / `D*` / `ADR-*`）追蹤，不因螺旋而失序。

## Alternatives

| 方案 | 為何否決 |
|---|---|
| 維持四階段瀑布 | 缺口需實作才能收斂；純規格推演風險高 |
| 純 prototype（無文件） | 違反「文件即工程基礎」的專案存在理由 |
| 雙軌（規格/實作各自獨立演化） | 易漂移，失去單一真實來源 |
