# owx 文件標準（document-standards.md）

> 版本：v0.4　|　日期：2026-10-17　|　狀態：Draft
> 目的：owx 的存在理由就是「**文件即工程基礎**」。因此文件本身必須**規格化、可追溯、可演化**——文件標準不是行政要求，是產品能力的一部分。

---

## 0. 第一原則

> **文件是知識資產，不是附件。** 每份文件都必須可 diff、可審核、可進 git、可被 RAG 佐證、可被 version 化。

任何文件的撰寫，都要問：**這份文件將來能否被檢索、被引用、被驗證、被演化？**

---

## 1. 文件類型

| 類型 | 位置 | 用途 | 前綴/命名 |
|---|---|---|---|
| **規格（Spec）** | `docs/spec/` | 需求（FR/NFR/邊界/來源對映）| `*-requirements.md`、`SRS-*` |
| **設計（Design）** | `docs/design/` | 技術設計（模組/介面/資料模型/狀態機/前端/測試）| `<主題>.md`（如 `harness-architecture.md`）|
| **架構決策（ADR）** | `docs/adr/` | 重大技術決策 | `ADR-NNNN-<slug>.md` |
| **規範（Standards）** | `docs/standards/` | 強制工作規範 | `<主題>-standards.md` |
| **知識庫（KB）** | `docs/kb/` | 參考資料（**非需求依據**）| `docs/kb/<主題>/` |
| **計畫（Plan）** | `.omo/plans/` | 執行計畫 | `*.md` |

- **知識庫不是規格**：與規格衝突時以規格為準；僅有知識庫而無需求條文者**不得實作**。
- 新增知識庫一律 `docs/kb/<主題>/`，不另開 `docs/` 頂層資料夾。

## 2. 通用格式

### 2.1 檔名
- **kebab-case**（如 `base-core-requirements.md`）；ADR 用 `ADR-NNNN-` 前綴。
- 檔名需自我說明；避免 `doc1.md`、`notes.md`。

### 2.2 表頭（每份文件必備）
```markdown
> 版本：v0.1　|　日期：YYYY-MM-DD　|　狀態：Draft | Review | Stable | Deprecated
> 來源：<從何而來 / 依據>
```

### 2.3 語言與術語
- 繁體中文為主；技術名詞、程式識別碼、產品名保留英文。
- 術語首次出現給英文對照（如「基礎核心（base core）」）。

### 2.4 連結
- 一律**相對連結**（`../spec/x.md`）；禁用絕對本機路徑於正式文件。
- 提交前確認**無懸浮連結**（連結目標存在）。

### 2.5 文件關聯（分檔分工）
- **原則：分檔分工，避免單一文件過大**——過長的單檔會稀釋脈絡、增加 AI/人為幻覺風險。
- 每份文件**必備**三要素：
  1. **定位聲明**：本檔是什麼、**不是什麼**（範圍界線）。
  2. **上下游連結**：以相對連結指向父／子／同級文件。
  3. **單一來源**：他處以連結引用，**不複製**內容（見 §7 撰寫原則）。
- **規格分層建議**：`*-requirements.md`（需求清單，逐條原子）↔ `functional-spec.md`（整合規格：架構／交互／驗收）↔ 外部載體規格（如 ow 的 `ow-workspace-layout.md`）。
- 拆分僅為治理，**不得**因此失去可追溯性：跨檔仍以穩定 ID（`FR-*`／`NFR-*`／`ADR-*`／`D*`）互指。

## 3. ID 規則（可追溯的基礎）

| 類型 | 規則 | 範例 |
|---|---|---|
| 功能需求 | `FR-<群>-<序>` | `FR-A-1`、`FR-DOC-3` |
| 非功能需求 | `NFR-<序>` | `NFR-1` |
| 架構決策 | `ADR-NNNN` | `ADR-0001` |
| 決策待辦 | `D<序>`（於 `AGENTS.md` §9）| `D1` |

- **每個需求、決策都給穩定 ID**——這是 traceability（需求↔測試↔實作）的前提。
- ID 一旦發佈**不改號**；廢除則標 `Deprecated` 並註明取代者。

## 4. 各類型標準

### 4.1 規格（Spec）
必含小節：
1. **目的、方法、範圍**（IN / OUT）
2. **功能需求**（FR，逐條、原子、可驗證）
3. **非功能需求**（NFR）
4. **邊界**（做什麼 / 不做什麼）
5. **來源對映與授權**（能力來自何處 + 授權）← owx 特有，見 §5
6. **缺口 / 待決**

### 4.2 架構決策（ADR）
必含：`Status`、`Context`（背景與問題）、`Decision`（決策）、`Consequences`（後果與取捨）、`Alternatives`（被否方案與理由）。

### 4.3 規範（Standards）
- 每條規範標明是**規範要求**還是**現況**。
- 若二者有落差，**明列「現況落差（待整改）」**——嚴禁把「未來該做」寫成「已做」（ASM 曾因混寫而被稽核修正）。

### 4.4 設計（Design）
- 位置 `docs/design/`；檔名 `<主題>.md`（如 `harness-architecture.md`、`interfaces.md`、`data-and-state.md`、`frontend.md`、`testing.md`）。
- 必含：**定位**（本檔是什麼／不是什麼）、**與規格／ADR 的關聯**（相對連結）、**圖**（架構／流程／狀態／ER 一律 Mermaid）、**可實作的決策與理由**。
- 每份設計須標明所依據的 `FR-*`／`ADR-*` ID。
- **不含**：實作程式碼；也不重抄需求條文（需求屬 Spec，連結引用）。

## 5. 授權標註（owx 特有，強制）

任何規格/設計文件提到外部元件，**必標授權**：

```
| 能力 | 來源 | 授權 | 處置 |
|---|---|---|---|
| ... | opencode | MIT | 可重用 |
| ... | omo | SUL-1.0 | 僅回溯，自建 |
```

- 詳見 [`governance/licensing.md`](governance/licensing.md)。
- 未標授權的外部元件視為**未定案**，不得進交付物。

## 6. 圖表標準：架構／流程／互動一律用 Mermaid

> **規則**：文件中的**架構圖、流程圖、互動／時序圖**（及狀態、資料模型），一律以 **Mermaid** 描述；**禁止** ASCII art、外部截圖、二進位圖檔。

理由（對齊 §0「文件是知識資產」）：
- **可 diff／可審核／可進 git**：Mermaid 原始碼是文字；點陣圖做不到。
- **機器可讀**：Mermaid 即結構化文字，可被 RAG / GraphRAG 解析，直接餵養未來的統一知識圖。
- **無外部資產**：不引入圖檔，避免懸浮連結與二進位 blob。

型別對照：

| 圖的種類 | Mermaid 型別 | 典型用途 |
|---|---|---|
| 架構（分層／模組／部署）| `flowchart` / `graph` | 三層架構、微服務邊界、部署拓撲 |
| 流程（步驟／決策）| `flowchart` | 工作流、clean-room 流程、PR 閘門 |
| 互動／時序 | `sequenceDiagram` | agent↔subagent 委派、SSE 事件流 |
| 狀態（生命週期）| `stateDiagram-v2` | session / endpoint / 任務狀態 |
| 資料模型（關聯）| `erDiagram` | 知識圖、ontology 關係 |

規範：
1. **圖必有說明**：每張圖需有 caption 或前後文，不得只有圖。
2. **文為主、圖為輔**：圖用於摘要；細節仍以條文/表格為準，**圖與文不一致時以文為準**。
3. **ID 一致**：圖內引用的 ID（`FR-*` / `ADR-*` / `D*`）須與正文相同。
4. 既有 ASCII 圖列為**待遷移**（見下方「現況落差」）。

**現況落差（待整改）**
- `AGENTS.md` §3 架構圖、`docs/spec/base-core-requirements.md` §2 架構視圖目前為 ASCII，須遷移為 Mermaid。

## 7. 撰寫原則

1. **原子**：一條需求講一件事；可獨立驗證。
2. **可驗證**：寫「可被測試/觀察的結果」，不寫「感覺良好」。
3. **事實 vs 願望分離**：明確標「現況」與「目標」。
4. **不重複**：單一來源；他處以連結引用，不複製內容。
5. **機器可讀傾向**：結構化（表格、ID、清單）優先於散段落——為了將來的 GraphRAG。
